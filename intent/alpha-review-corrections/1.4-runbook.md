# Box 1.4 runbook: clean-machine proof

Fresh GCE VM executes the published onboarding literally end to end
against the rc.12 candidate, then is destroyed. Anything done here
that the onboarding page does not say is a finding against the page,
not improvisation.

## Machine

- `e2-medium` (2 vCPU, 4GB), `europe-west1-b`, stock Debian image.
  Micro instance class per the box; medium is the smallest shape
  that builds Magento images without OOM (documented here so the
  choice is reviewable, not silent).
- Attached service account: dedicated `rsl1-cleanvm@digital-lab-341608`
  (created for this proof, deleted after). Granted exactly the roles
  onboarding's prerequisites imply: compute, container, sqladmin,
  secretmanager, storage, serviceusage, billing viewer,
  logging/monitoring viewer, artifactregistry writer. No owner, no
  editor: the proof also validates the documented grant set, and any
  missing permission fails loudly here first.
- Ambient ADC only (metadata server). No keys copied to the VM, no
  `gcloud auth login`. The operator's workstation credentials never
  touch the machine.

## Inputs staged from the workstation (the pilot's existing assets)

- `shop-ce-no-vendor.tar.gz`: clean Magento 2.4.9 tree
  (`composer create-project`, lock committed, no vendor). This stands
  in for the pilot's own shop checkout, which onboarding assumes.
  Transferred via `gcloud compute scp`.
- Nothing else. The MageLift tree comes from the release tarball per
  the onboarding page; base images build on the VM; the provider and
  CLI come from the release.

## Shop git remote

`magelift build` requires a git checkout with a remote (provenance).
The pilot's tree has a real remote; the proof uses a bare repo on the
VM as origin (`git init --bare factory.git`, `git remote add origin
<path>`). Real git mechanics, no network, dies with the VM. The
provenance URL records the file path honestly.

## Sequence (onboarding steps, literal)

1. Install with `MAGELIFT_VERSION=v0.1.0-alpha.1-rc.12`, `magelift
   version`.
2. `cd ~/shop`, extract the skeleton, `git init`, first commit,
   `magelift init --provider gcp`, fill project/domains, commit.
3. `magelift doctor` (ADC mint must pass on metadata credentials),
   `magelift config validate --env preview`.
4. `magelift providers install`, review, commit the lock.
5. Enable APIs (one command), `magelift bootstrap --env preview`.
6. Fetch the MageLift release tarball to `~/magelift-src`, create
   both registries, authenticate Docker, build and push both bases,
   recover digests, `cd ~/shop`, `magelift build --push` with
   digest-pinned bases.
7. `magelift deploy --env preview --yes` (email-disabled).
8. Per-surface verify, including the media hard gates: real admin
   upload; app-relative image URL with zero storage hosts in
   storefront HTML; retrieval on a fresh web pod; replacement;
   export/import round trip; negative tests (unauthenticated
   `/import_export/...` fails, stock denies hold for
   customer/downloadable/import/custom_options).
9. `magelift env sweep --dry-run` (mechanism exercise), then
   `magelift destroy --env preview --yes`.
10. Project-pinned repeat (`--project` flag) and generated-CI repeat
    per the box (short form: regenerate CI, run its lint/validate
    legs, confirm the sweep schedule entry).

## Teardown

- `gcloud compute instances delete` the VM (boot disk autodelete).
- Delete the `rsl1-cleanvm` service account and its bindings.
- Revoke nothing else: preview resources die with `destroy`; any
  leftovers fail the proof and get swept explicitly with notes.

## Records

- Full transcript (commands plus outputs) attached to the report.
- Dated notes for every deviation, however small.
- The VM's service-account grant list (proves the documented set).
