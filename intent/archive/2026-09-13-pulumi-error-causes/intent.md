# Intent: keep Pulumi update causes, including concurrent updates

## Problem

When `magelift deploy` or destroy fails inside Pulumi, the operator usually sees only `infrastructure update failed` (or preview/destroy). `Runner.run` returns that sentinel and drops the Pulumi cause, except for preview ownership errors. Two deploys colliding look the same as a graph bug. Pulumi 3.262 can match `ConcurrentUpdateError` through wrapped errors, but Magelift never wraps the cause, so that feature is unused.

## Evidence

`internal/automation/runner.go` returns `operationError` and not `fmt.Errorf("%w: %w", operationError, err)` on backend failure. Preview ownership is the only path that keeps a cause. Pulumi Automation API 3.262 unwraps wrapped errors for predicates such as concurrent update. Live two-deploy collision on a Magelift stack: not checked.

## Proposed outcome

A failed preview, update, or destroy still fails, and the printed error includes the Pulumi cause. A concurrent-update / stack-lock failure is distinguishable from a generic graph failure (exit code or message operators can match). Existing ownership errors stay classified. V1 priority: agency and SME operators without DevOps background cannot debug a bare sentinel, so this classification ships before the stable cut (see ROADMAP.md).

## Affected users and systems

Operators running `magelift deploy`, preview, or destroy. CI generated by `magelift ci`. `internal/automation` and the CLI commands that call it.

## Constraints

Do not leak secret values from Pulumi diagnostics. YAML-only user path. Do not invent certified claims. Pulumi mock tests must cover the classification. Keep preview ownership wrapping.

## Out of scope

Changing Pulumi lock backends. Retrying a locked stack automatically. Rewriting diagnostics streaming. `strings.CutLast` or json/v2.

## Open questions

Should concurrent-update be a dedicated exit code, or only a wrapped message under the existing update-failed code? Do preview and destroy use the same classification?
