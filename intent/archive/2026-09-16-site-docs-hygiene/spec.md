# Spec: site and docs hygiene

## Requirements

### Requirement: configuration.md generated header

`docs/configuration.md` SHALL open with the same do-not-edit generated header pattern as the other generated pages, emitted by the generator.

#### Scenario: header present with exact text

- **WHEN** reading `docs/configuration.md` after `make generate`
- **THEN** line 1 is `# Configuration reference`, line 2 is blank, and line 3 is exactly `This page is generated from the MageLift configuration schema. Do not edit it by hand.`
- **AND** `grep -F 'This page is generated from the MageLift configuration schema. Do not edit it by hand.' docs/configuration.md` exits 0
- **AND** line 4 is blank and line 5 resumes the existing prose starting with `` `magelift.yaml` uses schema version 1. Unknown fields are rejected. ``

### Requirement: generate-check stable across runs

The generated configuration outputs SHALL be deterministic and drift-free across consecutive generations.

#### Scenario: two runs produce no diff

- **WHEN** running `make generate` twice in succession, then `make generate-check`
- **THEN** `make generate-check` exits 0
- **AND** the second `make generate` produces no diff, verified by `git diff --exit-code -- docs/configuration.md schema/magelift.schema.json` exiting 0

### Requirement: sitemap outputs are untracked build products

`website/public/sitemap.txt` and `website/public/sitemap.xml` SHALL be untracked build products regenerated by the site build, not tracked source files.

#### Scenario: files untracked and ignored

- **WHEN** running `git ls-files website/public/sitemap.txt website/public/sitemap.xml`
- **THEN** the output is empty (both paths untracked)
- **AND** `grep -F '/website/public/sitemap.txt' .gitignore` exits 0
- **AND** `grep -F '/website/public/sitemap.xml' .gitignore` exits 0

#### Scenario: site build regenerates without dirtying the tree

- **WHEN** running `website/scripts/build-site.sh` (the same script `npm run build:site` invokes via `bash ./scripts/build-site.sh`, and CI invokes via `website/scripts/build-site.sh` in `.github/workflows/site.yml`)
- **THEN** `website/public/sitemap.txt` and `website/public/sitemap.xml` both exist on disk (regenerated by `website/scripts/generate-sitemap.py`)
- **AND** `git status --porcelain -- website/public/sitemap.txt website/public/sitemap.xml` outputs nothing (no tracked churn)

### Requirement: acceptance-dependencies orphan resolved via link

`docs/acceptance-dependencies.md` SHALL be resolved exactly one way: via the existing in-context links from the acceptance docs (link resolution; no nav entry, no orphan record).

#### Scenario: links present from both natural parents

- **WHEN** running `grep -rn 'acceptance-dependencies' docs/ mkdocs.yml website/ --include='*.md' --include='*.yml' --include='*.astro' --include='*.js'`
- **THEN** the output includes `docs/aws-acceptance.md` containing `[acceptance command dependencies](acceptance-dependencies.md)`
- **AND** the output includes `docs/gcp-acceptance.md` containing `[acceptance command dependencies](acceptance-dependencies.md)`

#### Scenario: link is the single resolution

- **WHEN** running `grep 'acceptance-dependencies' mkdocs.yml`
- **THEN** it exits 1 (no nav entry; link is the only resolution, no duplicate discovery path)

### Requirement: docs build stays green

The MkDocs build SHALL succeed with strict checks after all three fixes.

#### Scenario: make docs passes

- **WHEN** running `make docs` (which runs `"$(scripts/docs-venv.sh)/mkdocs" build --strict`)
- **THEN** it exits 0 with no strict-mode warnings or errors

## Design

### Fix 1: configuration.md header

**Implementation point: `internal/config.ReferenceMarkdown()` in `internal/config/schema.go` (lines 32-34), not `cmd/genconfig/main.go`.**

- `cmd/genconfig/main.go:24` is a thin writer: `{path: "docs/configuration.md", data: config.ReferenceMarkdown()}`. Its `--check` mode does a byte-exact comparison against whatever `ReferenceMarkdown()` returns, and its write mode dumps those bytes verbatim. It owns no content.
- `internal/config/schema.go:32-34` owns the content: `func ReferenceMarkdown() []byte` opens with the title plus the `` `magelift.yaml` `` prose. The header belongs in that first `WriteString`, between the `# Configuration reference\n\n` title and the prose.
- Rationale: content lives with content. This matches the existing pattern — `cmd/gendocs` emits title then `"This page is generated from the Cobra command tree. Do not edit it by hand.\n\n"` inside `render()`, and `cmd/gencertdocs` emits title then `"This page is generated from the source-dated MageLift capability catalog. Do not edit it by hand.\n\n"` inside its `render()`. Putting the header in `ReferenceMarkdown()` also keeps it covered by `TestReferenceMarkdownIsDeterministic` in `internal/config/schema_test.go`, which asserts directly on `ReferenceMarkdown()` output. Prepending in `genconfig` would split one page's content across two packages for no benefit.
- Wiring stays unchanged: `internal/config/generate.go` (`//go:generate go run ../../cmd/genconfig -root ../..`) plus `Makefile` `generate` regenerate the page; `generate-check` verifies it.

**Exact header text** (line 3 of `docs/configuration.md`, mirroring the two existing headers):

`This page is generated from the MageLift configuration schema. Do not edit it by hand.`

- Mirrors `docs/cli-reference.md:3` and `docs/evidence/current-capability-coverage.md:3`.
- "MageLift configuration schema" chosen over "YAML model" because it names the user-facing artifact (`schema/magelift.schema.json`, generated alongside the reference by the same `make generate`) rather than Go-internal jargon.
- Resulting file head:

```markdown
# Configuration reference

This page is generated from the MageLift configuration schema. Do not edit it by hand.

`magelift.yaml` uses schema version 1. Unknown fields are rejected.
```

- No other content change: the header is the only diff beyond the existing generated prose.

### Fix 2: sitemap outputs untracked

**Fix shape: gitignore (default stands), not dist redirect.**

- Generator: `website/scripts/generate-sitemap.py` resolves `public = website/public` and reads the built docs tree from `website/public/docs`; it writes `(public / "sitemap.txt")` and `(public / "sitemap.xml")`. Confirmed tracked: `git ls-files website/public/sitemap.txt website/public/sitemap.xml` currently returns both paths.
- Change:
  1. Append `/website/public/sitemap.txt` and `/website/public/sitemap.xml` to the website section of root `.gitignore`, directly after the existing `/website/public/docs/` line.
  2. Untrack without deleting: `git rm --cached website/public/sitemap.txt website/public/sitemap.xml`.
  3. No generator change; no sitemap content change.
- Rationale over dist redirect: two ignore lines plus untrack is the smallest correct change. A dist redirect would require rewriting the generator to know Astro's `dist/` layout, handling clean builds where `dist/` does not exist yet, and re-verifying the deploy path — all to move a file Astro already copies from `public/` to `dist/` by convention. `website/scripts/build-site.sh` already regenerates deterministically on every build, and `.github/workflows/site.yml` runs that script in CI and uploads only `website/dist`, so the committed blobs are never consumed as source.
- Nothing reads the committed files as source: the only in-repo references are the generator itself, `website/scripts/build-site.sh`, the runtime URL `Sitemap: https://magelift.dev/sitemap.xml` in `website/public/robots.txt`, and the serve-time MIME rule for `/sitemap.xml` in `website/public/_headers`. Both `robots.txt` and `_headers` refer to the served path, not the git blob. (`_headers` itself is deleted by `github-pages-deploy`; these two intents touch different lines and do not conflict.)

### Fix 3: acceptance-dependencies orphan

**Resolution: link (default stands). No file change required; the links already exist.**

- What the page is: `docs/acceptance-dependencies.md` is the shared `jq` / Mike Farah `yq` v4 preflight plus per-entrypoint local-command contract for the acceptance harnesses. Verified via `make acceptance-dependencies-check`.
- Evidence it builds but has no nav entry: `mkdocs.yml` Cloud-targets nav lists Capability matrix, AWS bootstrap, AWS acceptance, GCP acceptance, Packed RC1 sessions, and Experimental — no `acceptance-dependencies` entry; `exclude_docs` excludes only `evidence/` paths, so the page builds. It is also already enumerated in the built sitemap.
- Links already present (verified by the backlink grep):
  - Parent 1: `docs/aws-acceptance.md` — `[acceptance command dependencies](acceptance-dependencies.md)` in the Prerequisites section.
  - Parent 2: `docs/gcp-acceptance.md` — `[acceptance command dependencies](acceptance-dependencies.md)` in the Credentials section.
- Rationale for link over nav over record: the intent default was "link it if a natural parent exists, else nav it under Cloud targets" — two natural parents exist, and both link in exactly the right context (prerequisites/credentials, adjacent to the tool lists the page documents). Adding a nav entry would create a redundant third discovery path for a reference page best read in context. Recording it as an intentional orphan would be factually wrong — it is linked. Smallest correct change is therefore zero content change: the spec pins the existing links as the resolution and makes them verifiable via the grep scenarios above, closing the ambiguity the intent flagged.

## Gotchas / policy flags

- **Header must flow through the generator.** Hand-editing `docs/configuration.md` directly is prohibited by repo rules ("Do not hand-edit generated schema, CLI reference... Use `make generate`") and fails closed: `go run ./cmd/genconfig --check` byte-compares the file against `ReferenceMarkdown()` and exits 1 on any drift. Implement by editing `internal/config/schema.go`, then run `make generate` to regenerate.
- **Sitemap gitignore must not break the Pages deploy.** It does not: Astro copies `website/public/` into `website/dist/` at build time, so untracked-but-present sitemap files still ship locally; CI regenerates them from scratch via `website/scripts/build-site.sh` before `npm run build` and deploys only `website/dist`. The `git rm --cached` step untracks without deleting the working-tree files, so a local `website/dist` build keeps working immediately; a fresh clone regenerates on first `npm run build:site`.
- **`gendocs --check` is unaffected.** It byte-compares only `docs/cli-reference.md` against the Cobra tree. This spec touches no Cobra commands, so it stays green regardless; the link resolution adds no nav edit at all.
- **Humanizer does not apply.** No human prose changes: the header is a mechanical mirror of two existing generated headers, the `.gitignore` lines are paths, and the orphan resolution is verification-only with zero content edits. Per repo rules, mechanical header/nav/ignore changes skip humanizer and remove-ai-marks. If the implementer adds any human-facing sentence beyond the pinned header, that sentence alone goes through humanizer then remove-ai-marks.
- **`make docs` strictness.** `make docs` runs MkDocs `build --strict`; `strict: true` fails on broken links but not on nav orphans, consistent with the link resolution.
