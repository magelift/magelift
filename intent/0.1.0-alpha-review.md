# Review of the 0.1.0 alpha candidate

Date: 2026-09-17. Reviewed commit: `90e0dc120dee9f042d1bc70374c4207e6c789cbe`.
Implementation range: `8fd2304..90e0dc1`, following the original audit and
roadmap rewrite. The working tree was clean when review began.

## Verdict

**The direction is substantially better. The completion claims are ahead of the
implementation. I would not approve the final public alpha on this evidence.**

Keep the narrow GCP-first roadmap, the separate SDK and provider module, verified
binary distribution, and the explicit acceptance loop. Do not undo the useful
work. But reopen the affected outcomes from orders 4–7: installation is not
connected end to end, the production operator path still uses expiring saved
credentials, media persistence and restore are not implemented as the recipe
promises, and the plugin is still coupled to core internals.

Several changes solve a local piece of the problem and then describe the whole
problem as solved. Examples include an auth package tested separately from the
production client factory, a downloader tested independently of release metadata
and command discovery, and a module-download test described as publication
proof. These are integration gaps, not objections to the technology choices.

At review time, [release run 35215494505](https://github.com/magelift/magelift/actions/runs/35215494505)
was building **`v0.1.0-alpha.1-rc.1`**, at the reviewed commit. This is the
acceptance candidate, not the final `v0.1.0-alpha.1`. Its release job was still
running; lockfile generation, bundle verification, and attestation had not yet
completed when inspected. I did not stop it, change its metadata, push tags, or
perform cloud operations. Producing a candidate to test is sensible. Publishing
it as validated, or treating successful infrastructure provisioning as the
acceptance verdict, would not be.

## Scope and confidence

I reviewed the roadmap, all four remaining nonarchived intents, the seven new
archived intent/specification/plan/report sets, and the implementation change
inventory: 374 files, approximately 19,768 insertions and 6,272 deletions,
including moves. I traced the critical paths through release packaging,
installation, provider discovery, protocol dispatch, production registration,
credential use, deployment health, Magento lifecycle commands, media operations,
module publication, and CI coverage.

This is a risk-focused review of the full change set, not a claim that every
line of every moved provider file was independently verified. Existing tests
were run selectively. No live Magento deployment, full `make verify`, full
security scan, or multi-platform release matrix was run locally. Source-level
findings are identified as such; an unexecuted cloud scenario is not presented
as a reproduced cloud failure.

Codebase-memory was ready at generation `2026-09-17T11:16:49Z`; coverage checks
and direct source reads supported the cited paths. The findings do not rely on
graph absence alone. References below identify files and relevant line numbers
at the reviewed commit; later fixes may move them.

Severity: **P1** means fix before claiming the corresponding alpha outcome;
**P2** means a material correctness, maintenance, or evidence gap that needs an
explicit disposition. A packaging RC can exist while these issues are open.

## Findings

### R01 — P1: the published installation path cannot install and select GCP

This is a chain of connected defects, not just a missing documentation command.

1. [`.goreleaser.yaml`](../.goreleaser.yaml) puts only the CLI in the CLI archive;
   the provider is a separate raw release asset. The lockfiles are generated
   later by the workflow and uploaded separately.
2. [`website/public/install.sh`](../website/public/install.sh), lines 75 and
   116–135, extracts and installs only `magelift`. It fetches neither a provider
   lockfile nor provider artifacts. Its bootstrapped Cosign executable is in
   the temporary directory that the exit trap deletes.
3. [`internal/cli/providers.go`](../internal/cli/providers.go), lines 115–159,
   requires an existing project or executable-adjacent lockfile. There is no
   release-metadata bootstrap in that command.
4. [`internal/providerhost/generate.go`](../internal/providerhost/generate.go),
   lines 55–66, generates an artifact without `URL`, and with a relative bundle
   filename. `providers install` interprets an empty URL as “already bundled
   beside the CLI” and refuses when that binary is absent. Manually downloading
   the generated lockfile alone therefore does not repair installation.
5. [`internal/registry/registry.go`](../internal/registry/registry.go), lines
   51–67, uses a separate loader that only looks beside the executable. The
   cache-aware loader in [`internal/cli/subprocess.go`](../internal/cli/subprocess.go)
   is used later for the backend. Planning, hooks, and operations using the
   registry can fail before reaching it. Project lockfiles and `--cache-dir`
   accepted by the installer are not consistently honored by command execution.
6. Runtime verification shells out to `cosign` through
   [`internal/cosign/cosign.go`](../internal/cosign/cosign.go). The installer’s
   temporary bootstrap does not satisfy that dependency on a clean machine.
   [`internal/cli/ci.go`](../internal/cli/ci.go), line 302 onward, installs the
   CLI and Cosign but also omits provider metadata/artifact installation.

**Impact:** a clean install can pass `magelift version` and still be unable to
bootstrap or plan GCP. The docs currently claim release bundles ship providers
beside the CLI, which the archive configuration contradicts. A maintainer
manually placing the binary, bundle, and lock beside the CLI would bypass this
failure during acceptance and falsely prove the supported path.

**Fix:** have one resolver shared by registry, backend, hooks, and installation.
Define how a clean machine obtains authenticated platform-specific metadata,
downloads the selected artifact and bundle, and retains or provisions its
verifier. Generate usable URLs or deliberately bundle the required assets;
do not mix the two models. Project locks must control the version actually run.
Downloaded metadata must not be allowed to redefine the trusted publisher
without an explicit trust decision.

**Required proof:** a clean directory and user cache, no Go, no preinstalled
Cosign, and no artifacts beside the CLI. Install through the published script,
initialize GCP YAML, install the provider, then exercise a real command through
the production registry. Repeat with a project-pinned provider version and
generated CI. No manually assembled sidecars.

Owner: reopen `verified-provider-distribution`; prove the integration in
`reference-store-acceptance`.

### R02 — P1: production GCP operations still depend on the saved access token

The new [`providers/gcp/auth/auth.go`](../providers/gcp/auth/auth.go) is useful,
but its tests do not prove the released plugin uses it where the original bug
occurred.

The production main constructs `Server{Version: Version}` in
[`providers/gcp/cmd/magelift-provider-gcp/main.go`](../providers/gcp/cmd/magelift-provider-gcp/main.go).
`KubeClients` is nil. `Server.observe()` in
[`providers/gcp/plugin/day2.go`](../providers/gcp/plugin/day2.go), line 521,
passes that nil factory to `kube.NewObserveWithFactory`, which defaults to
`ClientFromOutputs`. That function, in
[`internal/cloud/kube/client.go`](../internal/cloud/kube/client.go), line 50,
parses the saved kubeconfig, unless an operator supplies the manual override.
The provider still generates that kubeconfig from an access token in
[`providers/gcp/runtime/runtime.go`](../providers/gcp/runtime/runtime.go),
lines 564–565.

Deploy candidate/runtime factories in
[`internal/providerhost/shim.go`](../internal/providerhost/shim.go), lines
445–469, also use `kube.ClientFromOutputs`. Exec preparation separately writes
the saved kubeconfig to a temporary file in
[`internal/cloud/kube/observe.go`](../internal/cloud/kube/observe.go), line 426
onward. Merely replacing the observation factory would not fix that exec path.

Fresh ADC is used in capability admission and the older GCP operations client.
That is real progress, but those are not the production observation/deployment
paths above. `NewRefresher` itself is exercised by its tests, not wired into
these paths.

**Impact:** status/health/log/exec and subsequent deployment work can still fail
after the stored token expires. A fresh `gcloud` login or an auth-helper unit
test does not establish that the actual request uses refreshed credentials.

**Fix and proof:** put GCP client construction under the provider with fresh,
refreshable credentials. Cover exec/tunnel launching as well as API requests.
Through the production plugin and core, supply an expired stored token and valid
ambient credentials; verify successful operations and that the stale bearer is
never sent. Test refresh failure and restart. The live expiry phase must omit
`MAGELIFT_KUBECONFIG` and other maintainer workarounds.

Owner: reopen `gcp-autonomous-provider`; live proof remains order 8.

### R03 — P1: GCS media and the planned media backup/restore path are not delivered

[`providers/gcp/storage/storage.go`](../providers/gcp/storage/storage.go)
creates a private GCS bucket with public access prevention, then exposes a
`storage.googleapis.com/<bucket>` URL. The runtime passes the bucket and URL
as `MAGELIFT_MEDIA_*` environment variables. Repository-wide source searches
found definitions/producers, but no consumer implementing Magento remote
storage from those variables. The GCP web pod specification has no persistent
media volume. There is no demonstrated bridge from an admin image upload to
that bucket and back to an anonymous storefront response.

The CLI defect is independently concrete:
[`internal/cli/env.go`](../internal/cli/env.go), lines 709–803, always calls
`newMediaS3Client` for `env media-sync`, including a GCP planned stack. It loads
AWS credentials and constructs an AWS S3 client. The command uploads a local
tree; it does not download a media backup. Yet the acceptance specification
names `env media-sync` in the backup/restore phase for GCS media.

**Impact:** an empty shop or a shop with image assets baked into its container
can look healthy while new uploads are ephemeral or unavailable. A bucket
existing is not evidence of application persistence. The documented restore
sequence cannot be assumed to work against GCP.

**Fix:** implement and configure a supported Magento media-storage mechanism,
including runtime authorization and public delivery; route CLI media operations
through the provider. Define both export and restore behavior. Do not make the
bucket public merely to hide missing application integration.

**Required proof:** upload new product media through Magento, view it without
cloud credentials, replace the serving pods, view it again, export the data,
restore into a fresh environment, and compare media contents. Restore must also
retain the correct Magento encryption key and prove usable application data.
Use a machine without AWS credentials for the GCP media test.

This gap predates parts of the extraction, but it is a blocker for the newly
claimed complete recipe. Owner: reopen `full-deployment-coverage` and include
real persistence/restore checks in order 8.

### R04 — P1: “deploy success means the application works” is still too strong

The rollout checks now inspect generation and updated replica counts. That is
a useful fix. The separate probe also improves on a static nginx response.
However, [`internal/cloud/kube/steps.go`](../internal/cloud/kube/steps.go),
line 298 onward, runs the Magento probe in a **new job**, not against the
serving application. [`internal/platform/workloads.go`](../internal/platform/workloads.go),
line 41, checks database status, a nonempty search-engine setting, and an
independent curl to the supplied search endpoint.

The serving nginx container still probes static `/health`, and PHP-FPM has no
corresponding application readiness check in
[`internal/cloud/kube/web.go`](../internal/cloud/kube/web.go). A PHP-FPM/web
integration failure can coexist with a successful CLI Magento job and healthy
nginx. A nonempty search-engine string plus a reachable endpoint also does not
prove Magento is configured to query that endpoint correctly.

`deploymentHealth` reads the first container image from the deployment template,
not the resolved image identity of all serving containers. Digest-pinned images
and rollout counters help, but the report’s “every served digest” style of
claim should be limited to what each platform actually checks.

**Fix:** retain the cheap scheduler checks, then require a bounded request
through the serving Magento path. Probe search through Magento’s effective
configuration, not just a separately supplied URL. Keep heavy catalog reindex
proof in acceptance. Test broken FPM/upstream routing, wrong effective search
host/engine, and stale rollout independently.

**Required proof:** a deliberately broken serving PHP path must cause deploy
failure even when the probe job can run `setup:db:status`; incorrect Magento
search configuration must not pass because some search server is reachable.

Owner: reopen `magento-deployment-safety`.

### R05 — P1 for the architecture promise: the provider is separately executable, not autonomous through the public SDK

The module extraction and removal of silent fallback are real improvements.
Nevertheless, the core and provider still share internal implementation types:

- The provider imports root `internal/platform`, `internal/cloud/kube`,
  `internal/automation`, and other internal libraries. Its specification
  explicitly relaxed “SDK-only” to allow this dependency.
- The core decodes `StoredPlan.DeployInputsJSON` into `kube.DeploySpec` and
  creates Kubernetes migration/probe jobs itself in `ShimOps.NewDeploySteps`.
  Changes to provider deployment behavior can still require a core release.
- Numerous protocol byte fields are documented as JSON encodings of root
  `platform.*` types. Naming an internal Go type in a field comment does not
  make its schema a separately governed public contract.
- The core retains a concrete `GCPTarget` type and hard-coded GCP runtime
  shims. Moving validation into the provider is progress, but new provider
  fields and arbitrary providers are not fully decoupled from the core.

The new `core-leanness` target checks only GCP imports. The production binary
still registers AWS, EKS, OVH, and Scaleway. A fresh dependency enumeration found
1,517 packages: 121 containing `aws-sdk-go`, 135 containing `pulumi`, 38
containing `scaleway`, 20 containing `ovh`, and 142 containing
`k8s.io/client-go`. These counts overlap; they are not binary-size measurements.
There were zero `cloud.google.com` and `providers/gcp` packages. **GCP extraction
passed; provider-independent core leanness did not.**

The accepted [ADR 0013](../docs/adr/0013-provider-plugin-contract.md) still
requires an SDK-only external provider, a provider-SDK-free core, provider-owned
operations, and typed progress. The archived order-5 spec/report weakened some
of those requirements without reconciling the ADR. Its spec even retains the
broader no-AWS/no-Pulumi/no-Kubernetes scenario while the implemented gate checks
only GCP.

**Recommendation:** finish the supported GCP boundary before replicating it for
AWS. Move execution of provider-specific deployment operations into the plugin;
put only the necessary operation contracts in the SDK. A small separately
versioned implementation-support module is an option if duplication is otherwise
unavoidable, but depending on the whole core’s internals is not the target.
Ship an alpha core registration that omits deferred implementations instead of
extracting every experimental provider before alpha.

If lockstep internal coupling is consciously accepted for a private engineering
preview, call it that and record the deferred boundary work. Do not archive the
autonomous-provider outcome as complete or tell future plugin authors that the
reference implementation proves SDK-only independence.

Owner: reconcile `provider-plugin-contract` and reopen `gcp-autonomous-provider`.

### R06 — P1 for publication claims: the provider publication test does not build a provider

[`tests/distribution/distribution_test.go`](../tests/distribution/distribution_test.go),
line 206 onward, publishes a temporary provider module, then runs
`go mod download -json`. It does not compile its packages or resolve the full
import graph. It patches an SDK requirement into the proxy’s `.mod` response,
while the zip was constructed beforehand from the unmodified source. It never
supplies the required root-module dependency. This proves that an archive can
be served, not that the provider can be consumed.

The separate SDK consumer build is meaningful and should stay. The provider
proof needs the same standard. Root and provider `go.mod` files still lack the
required MageLift module versions. With `GOWORK=off` and readonly/offline module
resolution, the root SDK lookup fails; the provider dependency walk reports
unresolved SDK/root-internal imports and missing sum entries. The provider’s
plain `go list ./cmd/...` can succeed because it does not load the dependency
graph; that is not a substitute for a build.

The report calls the missing requirements “pre-tag by design.” Module tags now
exist at this commit, but tagging unchanged manifests does not fill their
requirements. Workspace GoReleaser builds can still succeed, so this finding
does **not** predict that the current binary release job must fail.

**Fix and proof:** stage coherent SDK, root/support, and provider module
artifacts in a test proxy, with identical manifest content in `.mod` and zip;
resolve and compile the real provider with `GOWORK=off`. Complete the actual
tag/require/publication sequence using new commits and versions as necessary.
Do not rewrite already published tags to conceal the sequence problem.

Owner: reopen `verified-provider-distribution`.

### R07 — P1: the RC is not configured as a prerelease and publication precedes final checks

[`.goreleaser.yaml`](../.goreleaser.yaml), line 131 onward, sets release
preflight behavior but neither `prerelease` nor `make_latest`. GoReleaser’s
[documented defaults](https://goreleaser.com/customization/publish/scm/) are
`prerelease: false` and `make_latest: true`; the semantic-version suffix alone
is not the configured prerelease policy. The workflow invokes normal release
publication for this RC.

The workflow also uploads provider lockfiles and verifies bundles/checksums
**after** the GoReleaser publication step. Its cask job tests only
`magelift version`, after publication. Successful publication or that cask check
does not establish a complete, usable GCP distribution. New lockfiles are
uploaded outside the signed checksum set generated earlier; any automatic
lockfile bootstrap needs a considered authentication policy for them.

**Fix:** explicitly separate candidate/prerelease and stable/default channels.
Use a draft or equivalent staging flow until the artifact set and install test
pass, then expose the candidate for acceptance. A final alpha should remain
clearly labeled prerelease. Keep the default installer’s stable/latest behavior
separate from explicit alpha opt-in. If this RC has already been published,
correct its release metadata and communicate its validation status; do not
silently retag it.

This report does not assert that a public RC release already exists: the tag
release API returned 404 at the observation point, while the workflow was
still running. Owner: distribution and acceptance release procedure.

### R08 — P2: the lifecycle still has two authorities, and a flag is not a drain mechanism

Removing static-content deployment from the disposable migration job is the
right change. Requiring build-time static-content configuration is also useful.
But [`internal/platform/workloads.go`](../internal/platform/workloads.go),
line 13, still hard-codes the deploy/post-deploy sequence separately from
[`build/src/Magento/LifecyclePlan.php`](../build/src/Magento/LifecyclePlan.php).
The new `TestMagentoMigrationShellMatchesPHPDeploySequence` checks strings in
the Go function; it neither invokes nor compares the PHP authority. There were
no changes under `build/` or `images/` in this implementation range.

The maintenance change adds an acknowledgement and a manual runbook. It does
not verify maintenance state, stop cron/consumers, or restore their state. The
runbook says `bin/magento maintenance:enable` without establishing which
replicas share its maintenance flag; the GCP pod definition provides no shared
maintenance filesystem. New pods created by the rollout also need protection.

For an alpha explicitly restricted to compatible migrations, a documented
limitation is reasonable. The current flag does not justify claiming an
automated conservative incompatible-migration policy or a single lifecycle
authority. Requiring the acknowledgement on production commands cannot make
an incomplete multi-replica runbook safe.

**Fix:** invoke one authoritative lifecycle implementation. Either automate and
verify quiescence across web/cron/consumers, or reject unsupported incompatible
flows and document the remaining scope precisely. Test the actual lifecycle
contract, not two independently maintained strings that happen to agree today.

Owner: reopen `magento-deployment-safety`; production remains outside the
preview-only alpha proof.

### R09 — P2: moving GCP to a nested module removed it from ordinary CI coverage

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml), line 192, still runs
root `go test -race ./...`; the standalone SDK has its own job. The GCP-specific
job targets only `providers/gcp/floci/floci-gcp`. There is no corresponding
normal test/lint/vulnerability gate for the full nested provider module.
The synthetic suite remains behind a build tag without a normal CI invocation.
Provider-only `go.mod`/`go.sum` changes are not explicitly covered by the Go
path filter or its dependency-cache key.

Go workspace membership does not make a root `./...` pattern recursively test
other modules. The claim that “the full matrix runs in CI” therefore misses the
new module boundary. A release build compiles the plugin, but does not run its
unit, contract, or fault tests. The release workflow itself is triggered by
tags and does not require these test jobs on the tagged commit.

**Fix and proof:** enumerate the maintained modules in CI; add provider suite,
lint, dependency checks, and the synthetic suite explicitly, with correct path
filters and cache inputs. Require the appropriate same-commit checks before
candidate promotion. Demonstrate that a failing provider-only test prevents
promotion. Do not run the prohibited unbounded local race matrix to compensate.

Owner: order-5/7 completion correction, enforced before order-8 promotion.

### R10 — P2: several mutating RPC operations are incorrectly marked retryable on timeout

[`providers/gcp/plugin/server.go`](../providers/gcp/plugin/server.go), lines
46–66, assigns `fastRead` to `StateLock`, `StateUnlock`, `SecretSet`, and
`SecretRemove`. `fastRead.RetryableOnTimeout` is true. The dispatch timeout path
in [`providers/gcp/plugin/rpc.go`](../providers/gcp/plugin/rpc.go) copies that
flag into the returned operation error.

These operations mutate remote state. A timeout can occur after the mutation
commits but before its response arrives. In particular, retrying an unlock
after another owner acquires a lock is not justified by a generic “read” policy.
Even where a mutation can be made idempotent, that requires an operation-specific
contract. The comments and report say mutations are never retryable on timeout;
the table contradicts them.

**Fix and proof:** classify every operation by actual effect; mutation timeouts
must require reconciliation unless a tested idempotency/ownership mechanism
makes retry safe. Assert the timeout policy for all mutating operations, not
just Apply and Destroy. No automatic-retry incident was reproduced in this
review; the returned public contract itself is incorrect.

Owner: `gcp-autonomous-provider` protocol correctness.

### R11 — P2: updater recovery has a crash window despite its atomic-swap claim

[`internal/upgrade/upgrade.go`](../internal/upgrade/upgrade.go), line 207,
renames the current executable to `.prev`, then renames the new executable into
the original path. A process kill between those operations leaves the installed
command missing. Recovery on an ordinary returned error is implemented, but
there is no startup recovery path when the command itself is absent. Clearing
an old `.prev` before establishing a successful replacement also needs careful
recovery semantics.

**Fix and proof:** preserve the existing executable at its normal path until
the replacement rename, using a safe backup strategy appropriate to each
supported OS. Test interruption at each filesystem transition, as well as
self-check failure. Describe platform limitations honestly; two successful
renames in unit tests do not prove crash atomicity.

Owner: `verified-provider-distribution` updater guarantees. This need not block
a narrowly scoped first-install-only candidate, but the advertised upgrade
guarantee needs correction before relying on it.

### R12 — P2: the onboarding and pin sheet remain instructions to validate, not a proved recipe

[`docs/onboarding.md`](../docs/onboarding.md) still starts with `go install`,
does not include the new provider installation path, and goes from template /
bootstrap to deploy without an explicit immutable application build step. It
guides workstation users to `gcloud auth login`, while the code consumes ADC;
those are distinct credential configurations. Google documents the distinction
in its [ADC setup guide](https://cloud.google.com/docs/authentication/set-up-adc-local-dev-environment).
The declared interface needs to detect and explain the actual missing credential.

The SMTP check creates an **admin** user but asks for a **storefront** password
reset for it. Those are different account domains. Use the appropriate admin
reset flow or a test customer, and require evidence of message delivery. The
“SMTP or disabled” recipe option must not let the acceptance phase claim mail
proof while disabling it.

[`docs/alpha-recipe.md`](../docs/alpha-recipe.md) says everything is pinned,
but “OpenSearch 3,” “digest-pinned image,” and “recipe replica count” do not give
the actual digest/count. It also speaks of the region and recipe as proved
before the current loop has run. Record exact container digests, the application
source revision/build, effective config, scale, and region in a machine-readable
fixture and the evidence pack. The current page is a proposed recipe.

**Fix and proof:** execute the published onboarding literally on a clean
workstation, correcting missing steps instead of using unpublished commands.
Include a nonempty catalog, a new upload, the correct mail recipient, and the
generated scheduler running independently of the developer’s terminal. A
manual call to `env sweep` proves teardown, not autonomous scheduled expiry.

Owner: reopen `full-deployment-coverage`; finalize the recipe through order 8.

## What improved and should stay

- The roadmap now focuses on one complete supported origin and defers AWS
  parity, EU expansion, and a stable freeze. That is a better use of time.
- The GCP provider has its own module and real process boundary. The previous
  GCP fallback is gone; missing or invalid artifacts no longer deliberately
  select an embedded GCP implementation.
- Protocol negotiation, typed error codes, operation timeouts, and injectable
  test seams are useful foundations. Preserve them while correcting their
  ownership and timeout semantics.
- Initial CLI verification now requires its bundle and checksum, rather than
  opportunistically verifying only when Cosign exists. The updater attempts
  recovery on returned errors. Both are worthwhile even though the complete
  distribution flow and crash semantics need more work.
- Generation/replica rollout checks and moving static-content work to the build
  are substantive improvements. They should be extended, not removed.
- Synthetic fixtures are more honest about the limits of mocks. Original
  fixture content and explicit unsupported behavior are appropriate.
- Cost/security wording is more accurate, and the current evidence generator
  passes. The roadmap no longer equates a preview tuple with broad production
  certification.

### Evidence provenance qualification

The original operator seal was voided and 13 digests recomputed, with a provenance
note and no claimed new cloud run. That is more honest than silently repairing
hashes. However, corroborating a machine record with narrative reports from the
same historical run is weaker than recovering the original signed/raw input.
A new checksum establishes consistency of the retained record today; it does not
recreate the missing original attestation. Keep it labeled reconstructed
historical evidence. Use fresh order-8 evidence for current alpha release claims.

## Efficient correction sequence

1. **Fix candidate distribution before spending on GCP.** Correct the release
   channel metadata, generated artifact URLs/lock authentication, verifier
   availability, and shared resolver. Prove clean-machine registry execution.
2. **Repair the production provider boundary and auth wiring together.** Keeping
   deployment execution inside the provider makes credential ownership clearer.
   Resolve module dependencies and run a real external provider build. Exclude
   deferred providers from the alpha core rather than extracting all of them now.
3. **Complete the supported shop behavior.** Implement media persistence/export/
   restore; verify the serving application and effective search configuration;
   consolidate lifecycle execution. Keep unsupported production migration claims
