# Working on MageLift

MageLift deploys Magento from a shop’s `magelift.php`. Start with the [architecture guide](docs/architecture.md) for package ownership and [CONTRIBUTING.md](CONTRIBUTING.md) for setup.

## Local checks

- Install the PHP build dependencies once with `composer install --working-dir=build`. Use the Go toolchain in `go.mod`.
- Run `make test-fast` for the CLI, SDK and provider modules. Root `go test ./...` skips nested modules.
- Run `make verify-community` before submitting. For cloud changes use `make local-gates` for Pulumi mocks and Floci on AWS, GCP and Azure. Use `make ci-act-project` for generated shop workflows.
- Run `make generate` after changing project fields, command help or bundled skills. Check the generated diff. Run `make docs` for the public guides.

## Project rules

- MageLift reports what it tested. Give the test method, configuration and outcome. Preserve dated [run records](docs/evidence/README.md). Each shop owns its service versions.
- Repository CI uses Floci for cloud APIs. Shop workflows generated by MageLift deploy to the shop’s own account. A manual live run requires explicit authorization for a dedicated acceptance account, a cleanup owner and teardown on exit.
- Keep proprietary code, customer identifiers, credentials and Pulumi state out of the repository. This includes ece-tools and vendor patch databases. Follow the [clean-room rules](docs/provenance.md) and run `make check-clean-room`.
- Ask before a protected or production destroy, cloud spend, a release tag, public artifact publication or a history rewrite.

Contributor runbooks live in [contrib/skills](contrib/skills/). The CLI ships the [shop skills](agents/README.md). Update the relevant skill when its commands or configuration change.
