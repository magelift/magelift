  <name>Task 1: Guard the lint matrix against silently covering less</name>
  <files>internal/lintcoverage/coverage_test.go</files>
  <behavior>
    - Given the committed `ci.yml`, the union of the lint matrix package patterns expands to exactly the set `go list ./...` reports, modulo the paths `.golangci.yml` excludes.
    - Given a matrix entry whose pattern is deleted, the test fails and names the packages left uncovered.
    - Given a package covered by two partitions, the test fails and names the overlap — double-linting wastes a runner and hides which partition owns a failure.
    - Given a `ci.yml` whose lint job or matrix cannot be found, the test fails rather than passing vacuously.
  </behavior>
  <action>
Add a new package holding one test that reads `.github/workflows/ci.yml`, walks to the lint job's `strategy.matrix.include` entries, collects each entry's package patterns, expands them with `go list`, and compares the union against `go list ./...`.

This is the single most important guard in QUALITY-06. Without it, the requirement can be satisfied by linting fewer packages: `core`'s pattern list is explicit because a Go pattern cannot subtract `./internal/cloud/...` from `./internal/...`, so a new top-level directory joins the module without joining any partition, and the matrix stays green while checking less. The research names this as Pitfall 4 and the mitigation as mandatory.

Decode the YAML with the module's existing YAML dependency rather than adding one — the repo already pins a YAML package and this phase installs nothing. Locate the job by its key, not by position, and fail loudly if the structure is missing so a future `ci.yml` restructure cannot make the test vacuous. Expand the patterns by invoking `go list` on them; expand the reference set the same way so both sides use identical semantics. Subtract whatever `.golangci.yml` excludes by path so the assertion matches what the linter would actually inspect, and state the excluded set in the failure message so a reader can tell an exclusion from a gap.

Put it in its own small package so it does not drag `ci.yml` parsing into an existing domain package, and so the `core` lint partition picks it up. Follow the repo's test conventions exactly: standard-library `testing` only, plain `if got != want { t.Fatalf(...) }`, no assertion library, table-driven subtests where the cases vary. Do not add testify or any other test dependency.

Write the test before the assertion set is final: run it, watch it fail against a deliberately shortened matrix pattern, then restore the pattern and watch it pass. A guard that has never been seen to fail is not a guard.
  </action>
  <verify>
    <automated>GOMAXPROCS=1 GOFLAGS=-p=1 go test -race ./internal/lintcoverage/ -count=1 -v</automated>
  </verify>
  <done>The test passes against the committed matrix, and was observed failing when one partition pattern was temporarily removed. Its failure message names uncovered packages individually.</done>
  <reversibility rating="reversible">A new test file in a new package; deleting it restores the prior state.</reversibility>

<task type="auto">
  <name>Task 2: Settle whether `go test -race ./...` fits the runner</name>
  <files>docs/lint-policy.md, .github/workflows/ci.yml</files>
  <precondition>Plan 01-01's `go-verify` job exists and has reached the `go test -race ./...` step in at least one CI run, so there is a log to read rather than a prediction to make.</precondition>
  <action>
`go test -race ./...` has never executed in CI, and `-race` roughly doubles per-package memory over a graph that peaks near 8.5 GB when the four provider SDKs are linked into one binary. Whether it fits 7 GB is genuinely unknown; the research flags it as assumption A5 and asks the plan to pre-budget the contingency rather than discover it late.

Take the measurement in both places and record both numbers. Locally, run the suite serially — `GOMAXPROCS=1 GOFLAGS=-p=1` in a plain Terminal, one invocation, never a parallel or multi-platform variant, per AGENTS.md's kernel-panic history on this machine — and record wall time and peak resident memory. In CI, read the `go-verify` job log from plan 01-01's run and record whether the step completed, its duration, and whether the job approached its `timeout-minutes`.

If CI passed, write both figures into `docs/lint-policy.md` alongside the lint measurements, note that they were taken on the private-repo 2 vCPU / 7 GB runner class, and stop — no workflow change is needed.

If CI failed on memory or was reaped, partition the test step by the same six package groups the lint matrix uses, expressed as a matrix on `go-verify` or as a sibling `test` job, and re-verify. Do not raise a timeout instead: the failure signature to look for is a job dying with no test output after ten to thirty minutes, which is a reaped runner, not a slow one. Record the partitioning and its reason in `docs/lint-policy.md` so the narrowing is visible rather than folded into a config diff.

Either way, name the outcome explicitly in the plan summary. "It probably fits" is not an acceptable close for this task.
  </action>
  <verify>
    <automated>GOMAXPROCS=1 GOFLAGS=-p=1 go test -race ./... -count=1 &amp;&amp; grep -q 'race' docs/lint-policy.md</automated>
  </verify>
  <done>The local serial run passes with wall time and peak memory recorded; the CI outcome for the same command is recorded from a real job log; `docs/lint-policy.md` states both figures and the runner class they were measured on. If CI needed the test step partitioned, that change is committed and re-verified green.</done>
  <reversibility rating="reversible">Either a documentation-only change or a workflow-only change; both revert cleanly.</reversibility>

Left to normal filtering there is no run in which all eight execute together, which is precisely how the repository accumulated a green badge over a job that was being skipped.

Trigger the force-all dispatch on `main`, wait for it, then read every job's conclusion and map them onto the eight targets: `generate-check` and `cli-docs-check` and `fmt-check` and `test` and `license-check` in `go-verify`, `php-test` in the `php` matrix, `docs` in the `docs` job, `workflow-check` in `workflow-lint`. Every one must be `success`; `skipped` is not acceptable for this run, because the whole purpose of the dispatch is to defeat skipping. Record the run URL and the per-target conclusion table in the plan summary — that table is the phase's evidence for criterion 1.

The `php`, `docs`, and `workflow-lint` jobs have run before, but `generate-check`, `cli-docs-check`, `license-check`, and `govulncheck` have never completed in CI, so any of them may be red for reasons nobody has seen.
