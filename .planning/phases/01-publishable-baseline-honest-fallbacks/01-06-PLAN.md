QUALITY-08 asks for a regression test for that specific fix, and criterion 3 asks for min, cap, and cap plus one.

  <name>Task 2: Assert the MKS node-pool dependency ordering from recorded dependencies</name>
  <files>internal/cloud/ovh/runtime/runtime_test.go</files>
  <behavior>
    - The node pool records a dependency on the cluster.
    - The Kubernetes provider records a dependency on the node pool.
    - The web Deployment records a dependency on the node pool.
    - The web Service records dependencies on both the node pool and the web Deployment, proving the extra Service dependency added to the pair rather than replacing it.
    - The cron Deployment records a dependency on the node pool.
    - Removing the pool from any of those dependency lists makes the corresponding assertion fail — the test is checked against a deliberate regression once before being trusted.
  </behavior>
  <action>
Create the package's first test file with a Pulumi mock that captures dependency URNs, then assert the ordering the fix in commit `37081b7` established: MKS schedules pods and runs the load-balancer controller on pool nodes, so workloads must depend on the pool and not merely on the cluster.

Capture the dependencies from the mock's resource arguments, which carry the incoming register-resource request; that request holds the dependency URNs the engine actually received. Do not assert on the order of the recorded-resources slice as a proxy — the Go SDK registers resources concurrently, so slice order reflects goroutine scheduling and an order-based test would be flaky rather than wrong-once. No existing test in this repository uses the request field, so this is a new pattern here; write the capture helper small and obvious, guarding against a nil request.

Match dependency URNs by substring rather than by exact value, so a change to the project or stack name in the mock harness does not break the assertion. Structure the helper so a missing resource and an unsatisfied dependency produce different failure messages — one means the graph changed shape, the other means the ordering regressed, and they need different fixes.

Follow the repo's Pulumi test conventions: a per-package mock type with a mutex-guarded slice, resources driven through the component constructor under `pulumi.WithMocks`, a valid-baseline argument factory with targeted mutation per case, standard-library `testing` only.

Do not extend this assertion to the Scaleway or GCP Kubernetes runtimes in this phase. QUALITY-08 is scoped to the two OVH bugs, and the shared Kubernetes layer that would make a cross-provider assertion natural arrives in Phase 6. Leave a marker comment in the new file naming that ceiling: state that the same assertion applies to the sibling Kapsule and GKE adapters and that Phase 6's shared layer is the place to lift it, so the deliberate stopping point is visible instead of looking like an oversight.

  <action>
Add one test asserting that Scaleway creates a single private network carrying the whole configured range, regardless of how many zones the arguments name.

This is the honest reading of criterion 3's "for every provider" clause. Scaleway has no subnet index and no carve function — the Magento contract wants subnet identifiers, and a Scaleway private network is itself the attachment unit, as the comment in the source states. There is nothing to place at a cap or one past it. What can regress is the model: someone adding per-zone carving here would break the attachment contract silently, and this test makes that change loud.

Assert on the recorded resources through the existing mock in this file rather than adding a second harness, and vary the zone count across subtests so the invariant is clearly about the model and not about one input. State in the test's doc comment that Scaleway deliberately does not carve, and why, so the test reads as documentation of a decision rather than as a weaker version of the other providers' boundary tests.
