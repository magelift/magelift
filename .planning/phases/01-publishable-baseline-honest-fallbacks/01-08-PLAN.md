<objective>
Make every unimplemented day-2 surface say what it is, which target it applies to, and what tier that target holds.

Purpose: `notSupported` already names the capability and the target but not the tier, and three surfaces — logs, health, and cost — bypass it entirely with their own messages, while the three port helpers name nothing at all beyond "this target". Meanwhile the fifteen unsupported methods in each of the two experimental stub shells have no test, so nothing proves they return the sentinel rather than a nil-success path. The counts are exact: fifteen in the OVH shell and fifteen in the Scaleway one, and the two files are parallel apart from a comment.

Output: A tier-naming message shape applied uniformly, an enumeration test shared by two subtests, and a source-level guard that survives refactoring.
</objective>

  <name>Task 1: Name the certification tier on every unsupported day-2 surface</name>
  <files>internal/cli/ports.go, internal/cli/logs.go, internal/cli/health.go, internal/cli/cost.go, internal/cli/stub_module_test.go, internal/cli/ports_test.go</files>
  <behavior>
    - An unsupported surface reached through `notSupported` produces a message naming the surface, the provider, the runtime, and the certification tier, and exits 2.
    - The logs, health, and cost surfaces produce that same message shape rather than their own variants.
    - Each of the three port helpers, when its module exposes no implementation, produces a message naming the surface, the provider, the runtime, and the tier.
    - An experimental target's message states the experimental tier; a certified target's message states the certified tier — asserted in both directions, so the test cannot pass by printing a constant.
    - The leading portion of the cost message up to and including the target introduction is unchanged, so plan 01-03's cost tests keep passing without edits.
  </behavior>
  <action>
Add the certification tier to the shared `notSupported` helper, then route the three surfaces that bypass it through it and give the three port helpers the same treatment.

Choose one message shape and use it everywhere: the surface name, then the target as provider and runtime, then the tier, then the existing trailing qualifier. The constraint from plan 01-03 is that the leading portion through the target introduction must survive byte-for-byte, because that plan's cost tests assert on it; append the tier after the provider and runtime rather than inserting it earlier. Run plan 01-03's cost tests as part of this task's verification — if they need editing, the message shape was changed in the wrong place.

Read the tier from the planning port, not from a cloud package. `platform.PlannedStack` already exposes the tier and so does `platform.StackModule`, which is what the port helpers hold. This is the sanctioned crossing under ADR 0002 and ADR 0004, and it matters concretely rather than formally: importing a cloud package into `internal/cli` re-links the Pulumi provider SDKs and revives the roughly 8.5 GB peak-memory failure that made `gendocs` unbuildable. Do not push tier strings down into the adapters either — the adapter returns a sentinel, and only the CLI knows the planned stack.

Delete the three bespoke messages in logs, health, and cost rather than leaving them beside the shared one. Two shapes for the same condition is how the current inconsistency arose.

Extend the CLI test stubs so this is testable at all. The stub planned stack hard-codes the certified tier, so no test can currently reach the experimental branch. Add a tier field that the stub reads instead of the constant, and add a second stub module describing an experimental target — the registry rejects duplicate provider and runtime pairs, so it needs a distinct descriptor. Keep both in the existing stub file so `internal/cli` stays free of cloud imports.

Assert both directions. A test that only checks the experimental case would also pass if the tier were printed unconditionally, which is one of the ways this requirement can be satisfied on paper and not in fact.
  </action>

<task type="auto" tdd="true">
  <name>Task 2: Enumerate all thirty unsupported methods and assert no nil-success path</name>
  <files>internal/cloud/ovh/stack/ops_test.go, internal/cloud/scaleway/stack/ops_test.go</files>
  <behavior>
    - Each of the fifteen unsupported methods on the OVH stub shell returns an error matching the not-supported sentinel.
    - Each of the fifteen on the Scaleway shell does the same.
    - Each method that returns a value alongside its error returns that value's zero form — an empty result struct, a nil slice, or an empty string — so "no nil-success path" is asserted rather than assumed.
    - The deploy-steps method returns the sentinel and a nil step set.
    - The five module accessors return the stub shell rather than nil, so the CLI reaches the sentinel instead of a nil-pointer path.
  </behavior>
  <action>
Add an enumeration test per provider, driving every method by hand through an explicit table of method name and invoking closure. Do not use reflection: reflecting over an unexported type is fragile, and an explicit table doubles as documentation of the surface, which is worth more here than brevity.

The second assertion is the one that makes this requirement real rather than decorative. Asserting only that the sentinel comes back leaves the door open to a method that returns a populated result alongside the error, which a caller ignoring the error would treat as success. Assert the zero value of every returned value as well.

The two files are parallel in shape, so express the cases as one table consumed by both packages' tests rather than as two divergent copies — but keep each test in its own package file, since these are white-box tests on unexported types and cannot share a package. Duplicating the table literal across two files is acceptable and preferable to creating a cross-adapter test helper package, which would couple two providers and cut against the split-by-port-nature guardrail.

Follow the repo's test conventions exactly: standard-library `testing`, `errors.Is` for the sentinel, plain fatal comparisons, table-driven subtests.
  </action>
  <verify>
    <automated>GOMAXPROCS=1 GOFLAGS=-p=1 go test -race ./internal/cloud/ovh/stack/ ./internal/cloud/scaleway/stack/ -count=1 -v</automated>
  </verify>
  <done>Thirty subtests pass across the two packages, each asserting both the sentinel and the zero value. The five module accessors are asserted non-nil in each.</done>
  <reversibility rating="reversible">Test-only addition.</reversibility>

<task type="auto" tdd="true">
  <name>Task 3: Guard the stub shells against a silently added nil-returning method</name>
  <files>internal/cloud/ovh/stack/ops_test.go, internal/cloud/scaleway/stack/ops_test.go</files>
  <behavior>
    - Given the committed stub shell source, every method on the unsupported type returns the not-supported sentinel in its error position.
    - A method added to the unsupported type that returns a nil error makes the guard fail, naming that method.
    - The lock-acquisition method on the operations type is the single recognised exception, listed explicitly with its reason, so the exception is visible rather than implicit.
    - A source file the guard cannot parse makes it fail rather than pass.
  </behavior>
  <action>
Add a structural guard that reads the stub shell's own source with the standard library's Go parser, walks each method declaration on the unsupported type, and checks that every return statement supplies the not-supported sentinel in its error position.

Parse rather than pattern-match the text. A text search over the file would be defeated by formatting and would count occurrences in comments, and the failure mode this guard exists to catch is a future contributor adding a sixteenth stub method that returns nil — a structural property, so check it structurally. The parser is in the standard library, so this adds no dependency.

List the lock-acquisition method as the one recognised exception with its reason stated in the test, because it deliberately returns a working release function today. Plan 01-10 revisits exactly that exception; the guard should make it a named, visible carve-out so that plan has something concrete to change rather than a convention to discover.

Fail on a parse error rather than skipping. A guard that quietly passes when it cannot read its input is worse than no guard, because it reports confidence it does not have.

Phase 6 anticipates a guard of this kind for the real implementations that will replace these shells. Write it so it keeps working when a method body becomes a real implementation: a method that no longer returns the sentinel should be removed from the guard's expected set deliberately, and the guard should say so in its failure message rather than simply going red.
  </action>
