<objective>
Turn two silent-growth risks into loud test failures.

Purpose: An IAM permissions boundary that outgrows 6144 characters stops applying, which is a privilege-escalation risk rather than a cosmetic one — and today only two of the nine rendered documents are size-checked, both inside a test whose name is about least privilege. Separately, the AOSS serverless capacity validator enforces a step rule AWS does not publish anywhere, so the honest deliverable is a test that locks MageLift's own rule plus a recorded provenance, not a test that pretends to encode AWS behaviour.

Output: One dedicated quota test covering all nine documents with a margin warning, one accept-and-reject OCU table, and a provenance record in code and in the knowledge bundle.
</objective>

<task type="auto" tdd="true">
  <name>Task 1: Size-guard all nine rendered IAM policy documents against their real quotas</name>
  <files>internal/cloud/aws/bootstrap/identity_test.go</files>
  <behavior>
    - Each of the three managed policies — the CI permissions boundary, the state boundary, and the build boundary — is under 6144 characters.
    - Each of the three inline role policies — CI, state, and build — is under 10240 characters.
    - Each of the three role trust policies — CI, state, and build — is under 2048 characters.
    - Any document exceeding 90 percent of its own quota fails with a message naming the document, its size, its quota, and the remedy.
    - The test fails with the document's own name, so a size regression identifies itself without reading the assertion.
  </behavior>
  <action>
Add one dedicated table-driven test enumerating every rendered document with the quota belonging to the API that submits it, and move the two assertions currently embedded in the least-privilege test into it so a size failure is no longer reported under an unrelated test name.

The quotas are not interchangeable and the mapping matters. Three documents are submitted as customer managed policies through `ensureManagedPolicy`, whose limit is 6144 characters: the CI permissions boundary, plus the state and build boundaries applied at `identity.go:269-271` and `identity.go:289-291`. Three are submitted as inline role policies through `ensureRoleSpec`, aggregate limit 10240. Three are role trust policies with a 2048 default that is raisable to 8192. Today only the first managed policy and the CI inline policy are checked; the other seven are unguarded, and two of the unguarded ones are boundaries — the exact control whose silent failure to apply is a privilege-escalation path.

Measure with `len()` on the marshalled string and add no whitespace-stripping step. AWS does not count whitespace, and `canonicalJSON` already emits compact JSON with no intra-string spaces in these documents (they hold actions, ARNs, and service prefixes), so `len()` is a sound upper bound. A stripper here would be dead complexity that looks like rigour.

Fail hard at the quota and also fail at 90 percent of it, with the second message telling the maintainer to move detail into an inline policy — the technique commit `8c3a4c6` used. The failure mode this requirement exists to catch is slow growth, and an at-the-limit-only test gives no warning until it is already too late to add one more permission. Cite the AWS quota page in a comment above the table so the numbers are traceable, and note that whitespace is excluded from AWS's count.

Reuse the existing `testIdentityPlan` helper for the plan fields and the existing boundary-rendering function for the CI boundary. Do not change any production file in this task — the documents are already the right size; only the guard is missing.
  </action>
  <verify>
    <automated>GOMAXPROCS=1 GOFLAGS=-p=1 go test -race ./internal/cloud/aws/bootstrap/ -run 'Quota' -count=1 -v</automated>
  </verify>
  <done>Nine subtests pass, each named for its document. The least-privilege test no longer carries size assertions. A deliberate padding of one document makes the corresponding subtest fail with a message naming that document and its quota — verified once, then reverted.</done>
  <reversibility rating="reversible">Test-only change; the production documents are untouched.</reversibility>
</task>

<task type="auto" tdd="true">
  <name>Task 2: Lock the serverless OCU validator with an accept-and-reject table</name>
  <files>internal/cloud/aws/search/search_test.go, internal/cloud/aws/search/search.go</files>
  <behavior>
    - Accepted values: 1, 2, 4, 8, 16, 32, 48, and further multiples of 16 above 32.
    - Rejected values: 0, 0.5, 3, 6, 12, 17, 24, 33, negative numbers, NaN, and positive infinity.
    - Range validation rejects a maximum below its minimum, a zero or negative minimum, and any non-finite bound, while accepting a maximum equal to its minimum.
    - The reject cases assert the validator returns false, not merely that some error occurred, so the table pins the rule rather than the caller.
  </behavior>
  <action>
Add a table over value and expected-validity pairs asserting `validServerlessOCU` directly, plus a companion table for `validCapacityRange`. Both are unexported and in the same package as the test, so no export or Pulumi run is needed — these are pure functions and the test should cost milliseconds.

The honesty constraint is the whole point of this task. AWS's published model for collection-group capacity limits documents only that the minimum fields accept values at or above zero and the maximum fields at or above one; it publishes no step rule at all, and the nearest documented granularity — multiples of two — belongs to a different API surface, the account-level settings. The published model therefore contradicts part of what MageLift enforces: MageLift rejects a zero minimum, which AWS documents as valid. So this test cannot prove what AWS accepts. It can only prevent MageLift's own rule from drifting silently, which is what QUALITY-03 asks for once read carefully.

Record that in a comment above the validator: state that the rule was derived empirically from a collection-group rejection observed on 2026-07-19 under commit `b8b957e`, that AWS publishes only the minimum and maximum floors for these fields, that the step rule is unpublished, and that it must be re-verified on the next paid AWS pass. Write the test's own doc comment the same way, so nobody later "fixes" the validator against the documentation and re-breaks a real deployment.

Do not add an upper bound to the validator in this phase. The documented account-level ceiling of 1700 OCU is tempting and the research calls it cheap, but it is a behaviour change no criterion asks for, and a wrong ceiling rejects a configuration that would have worked. Leave a marker comment naming the ceiling and the upgrade path instead: state that no maximum is enforced, name 1700 as the documented account-level figure, and point at the next paid pass as the place to confirm it before enforcing. That is the conservative call and it keeps the deliberate stopping point visible.
  </action>
  <verify>
    <automated>GOMAXPROCS=1 GOFLAGS=-p=1 go test -race ./internal/cloud/aws/search/ -run 'OCU|CapacityRange' -count=1 -v</automated>
  </verify>
  <done>Both tables pass with every listed accept and reject value present as its own subtest. The validator carries a provenance comment naming the commit and the date, and a marker comment naming the unenforced 1700 ceiling and its upgrade path.</done>
  <reversibility rating="reversible">Test additions plus comments; no behaviour change.</reversibility>
</task>
