<objective>
Stop the CLI from touching an experimental target quietly, and stop `deploy` from reporting success for work it did not do.

Purpose: An operator running `magelift deploy` against an experimental target today gets a Pulumi update and exit zero, with no Magento migrate, cutover, or health step and no message saying so — the code catches the not-supported sentinel and falls through with a comment explaining that only the infrastructure graph was updated. That is precisely the false success TRUST-02 exists to prevent, and it is not one of the thirty enumerated sentinel sites, so plan 01-08 could close its clause while leaving this intact. Separately, nothing anywhere warns that the selected target is experimental before mutating a real cloud account.

Output: A tier warning at the one choke point every command passes through, and a deploy path that either refuses or announces.
</objective>

<task type="auto" tdd="true">
  <name>Task 1: Warn at the planning choke point whenever the target is experimental</name>
  <files>internal/cli/lifecycle.go, internal/cli/lifecycle_test.go, internal/cli/stub_module_test.go</files>
  <behavior>
    - A mutating command against a target whose certification tier is experimental writes a warning to standard error naming the tier, the provider, and the runtime, and pointing at the capability matrix.
    - The warning appears before any infrastructure backend is constructed, asserted by using options with no backend factory so construction would fail loudly if it happened first.
    - A read-only command against the same target also warns — over-warning on an experimental target is correct, and a mutating-only flag threaded through eighteen call sites would silently regress the first time someone forgot it.
    - A certified target produces no warning at all.
    - The experimental AWS Kubernetes target warns, proving the gate is keyed on tier rather than on a provider list.
    - Structured output written with `-o json` remains parseable, because the warning went to standard error.
    - No confirmation prompt appears and the command does not block, even without the no-interaction flag.
  </behavior>
  <action>
Add the warning inside the planning choke point, unconditionally for every command rather than only for mutating ones. That function is the single funnel: eighteen call sites reach it, spanning preview, deploy, destroy, outputs, bootstrap, exec, ssh, cache flush, reindex, cron run, queue status, all three secret subcommands, all four state subcommands, promote, rollback, logs, health, cost, and login — and every one of them runs before any backend is created. A boolean parameter marking a call site as mutating would need threading through all eighteen and every future one, and the first forgotten value is a silent honesty regression, which is the exact failure this requirement targets.

Key it on the certification tier, never on a provider name. A provider allowlist of the three obvious experimental providers would let the experimental AWS Kubernetes target mutate silently, because it shares the certified provider's name. Allowlists rot; the tier does not. Read the tier from the planned stack the planning call already returns, which is the crossing ADR 0002 and ADR 0004 sanction, and add a test row for the AWS Kubernetes case so the distinction is enforced rather than merely intended.

Write to standard error. Structured payloads go to standard output through the shared writer, so a warning on standard error leaves json and yaml output parseable for machine consumers. Name the tier, the provider, the runtime, and the documentation page, and say plainly that day-2 operations may be unimplemented and that the target has no real-account acceptance evidence. Keep it to those facts: no account identifiers, no ARNs, no backend URL.

Do not add a confirmation prompt. TRUST-01 asks for a warning; a prompt would break the no-interaction contract and every CI usage, and there is no interactive human in the loop for this project's own automation.

Extend the test stubs only as far as needed, reusing the experimental stub module plan 01-08 added rather than adding another. Assert both directions and assert that no backend was constructed — a single-direction test would pass against a warning printed unconditionally, and a test that never checks ordering would pass against a warning printed after the backend was already talking to a cloud account.
  </action>
  <verify>
    <automated>GOMAXPROCS=1 GOFLAGS=-p=1 go test -race ./internal/cli/ -count=1 -v</automated>
  </verify>
  <done>The whole CLI package passes. The warning is asserted present for an experimental target and absent for a certified one, present for the experimental AWS Kubernetes target, emitted before any backend construction, and on standard error with structured output still parseable. No prompt was added.</done>
  <reversibility rating="reversible">A small addition inside one function plus tests; reverting restores silence.</reversibility>

<task type="auto" tdd="true">
  <name>Task 2: Stop `deploy` from reporting success for an infrastructure-only update</name>
  <files>internal/cli/lifecycle.go, internal/cli/lifecycle_test.go, docs/capability-matrix.md</files>
  <behavior>
    - `deploy` against a target whose operations port cannot supply Magento deploy steps, without the infrastructure-only flag, exits non-zero with a message naming the target, its tier, and specifically what was not performed.
    - The same invocation with the infrastructure-only flag succeeds, and writes a notice to standard error stating that Magento migrate, cutover, and health were skipped.
    - A target that does supply deploy steps is unaffected: the full deploy flow still runs, with no notice and no refusal.
    - A genuine failure to construct deploy steps — an error that is not the not-supported sentinel — still fails as it does today, distinctly from the refusal.
  </behavior>
  <action>
Change the fallback so the absent Magento deploy path is a decision the operator makes rather than one the CLI makes for them. When the operations port reports that deploy steps are not supported, refuse unless the infrastructure-only flag was passed explicitly; when it was passed, proceed but write a notice to standard error naming what was skipped.

The flag already exists on the deploy command, so this needs no new surface — only a change in who decides. Keep the existing distinction between the not-supported sentinel and a real construction error: the latter must keep failing the way it does now, and the two must produce different messages, because one means "this target cannot do that" and the other means "something broke".

Word the refusal so it is actionable: name the target and its tier, state that Magento migrate, cutover, and health cannot run on this target, and name the flag that proceeds with infrastructure only. Use the structured user-error type the repo already has for actionable CLI errors, so the cause and the next step are carried the way every other guided error in this codebase carries them.

Do not weaken this to a warning-only path. Criterion 5 permits announcing loudly or refusing without an explicit flag, and the maintainer scoped it to the stricter reading: refuse by default, proceed only on an explicit request. A warning alone still lets an unattended pipeline record a green deploy for a store that was never migrated.

Record the consequence where an operator will look for it. Add a line to the capability matrix stating that on targets without Magento deploy steps, `deploy` requires the infrastructure-only flag, so the behaviour change is documented rather than discovered.
  </action>
  <verify>
    <automated>GOMAXPROCS=1 GOFLAGS=-p=1 go test -race ./internal/cli/ -run 'Deploy|InfraOnly' -count=1 -v &amp;&amp; GOMAXPROCS=1 GOFLAGS=-p=1 go test -race ./internal/cli/ ./internal/deploy/ -count=1</automated>
  </verify>
  <done>All four behaviours have passing assertions, the refusal and the genuine-error paths produce different messages, the certified deploy flow is unchanged, and the capability matrix records the new requirement.</done>
  <reversibility rating="costly">This changes what `deploy` does for existing experimental-target users: an invocation that previously exited zero now exits non-zero until the flag is added. The code change reverts trivially, but the behavioural promise is operator-visible, so reverting after release would itself be a change worth announcing. Criterion 5 mandates this direction, so it is a scoped decision rather than an open one.</reversibility>
