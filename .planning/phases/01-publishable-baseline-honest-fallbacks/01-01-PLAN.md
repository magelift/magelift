<objective>
Make CI execute for the first time in the repository's history.

Purpose: The `go` job has never passed — failure ×11, cancelled ×4, skipped ×10, success ×0 across the last 25 runs. `golangci-lint run ./...` holds type information plus eight analysers' facts for ~84 packages spanning five provider SDK graphs in one process on a 2 vCPU / 7 GB private-repo runner, and the runner is reaped before the linter emits a single line. Nothing else in this phase can be trusted until this is fixed, because every other plan's evidence is a CI run that does not currently work.

Output: A gofmt-clean tree, a restructured `ci.yml` whose lint work is partitioned and whose cache is primed, a `.golangci.yml` with the two workarounds removed, and a CI run URL proving the whole pipeline green.

<task type="tracer">
  <name>Task 2: End-to-end green CI pipeline — one pass through every layer</name>
  <files>.github/workflows/ci.yml, .golangci.yml</files>
  <precondition>`gh` is authenticated against this repository with push access to `main`, and Task 1's gofmt commit is already pushed — otherwise the formatting step fails before lint runs and the run proves nothing.</precondition>
  <action>
Wire one complete path through every layer of the CI pipeline and prove it green in a real run. The layers are: change detection, cache priming, partitioned lint, the remaining Go verification steps, and the aggregate `CI passed` gate. Touch each one once, verify end to end, then let later plans expand outward from the proven shape.

Split today's monolithic `go` job into three jobs, all gated by the existing `changes` filter:

`cache-prime` — checkout, `actions/setup-go` with `go-version-file: go.mod`, then `go build ./...` bounded to a single process with `GOFLAGS=-p=1` and `GOMAXPROCS=1`, then an explicit `actions/cache` save of `~/.cache/go-build` and `~/go/pkg/mod` with `if: always()`. The explicit save with `if: always()` is the whole point: `setup-go`'s implicit post-step never runs when the runner is reaped, which is why every run to date started cold. Give the job `timeout-minutes: 20`.

`lint` — `needs: [changes, cache-prime]`, `timeout-minutes: 15`, `strategy.fail-fast: false`, and a six-entry `matrix.include`, each entry carrying a `name` and a `packages` string. The six partitions are forced by the import graph, not chosen: `aws` covers `./internal/cloud/aws/...`; `gcp` covers `./internal/cloud/gcp/...`; `ovh` covers `./internal/cloud/ovh/...`; `scaleway` covers `./internal/cloud/scaleway/...`; `aggregate` covers `./cmd/magelift/...` and is irreducible because `cmd/magelift/main.go` is the only file importing all four providers; `core` covers everything else as an explicit list. Derive the `core` list from `go list ./...` so it is complete — it must include `./internal/cloud/kube/...`, `./internal/build/...`, `./internal/automation/...`, `./internal/benchmark/...`, `./internal/config/...`, `./internal/containerrunner/...`, `./internal/cosign/...`, `./internal/deploy/...`, `./internal/health/...`, `./internal/infra/...`, `./internal/localdev/...`, `./internal/releasejournal/...`, `./internal/secretref/...`, `./internal/source/...`, `./internal/toolchain/...`, `./internal/topology/...`, `./internal/upgrade/...`, `./internal/usererr/...`, `./internal/cli/...`, `./internal/platform/...`, `./sdk/...`, `./cmd/genconfig/...`, and `./cmd/gendocs/...`. A Go package pattern cannot subtract `./internal/cloud/...` from `./internal/...`, which is exactly why this list is explicit and why plan 01-02 adds a test that fails when it drifts. Each entry runs `golangci/golangci-lint-action` at the SHA already pinned in this file, `version: v2.12.2`, with `args: ${{ matrix.packages }}`, and `skip-save-cache` set true on all but the `aws` entry so the matrix has one cache writer.

`go-verify` — `needs: [changes, cache-prime]`, `timeout-minutes: 25`, carrying the steps that have never run: the `gofmt -w` plus `git diff --exit-code` drift check, `genconfig --check`, `gendocs --check`, `go test -race ./...`, `govulncheck`, and the `go-licenses` check. Keep it independent of `lint` so a lint failure no longer hides whether the tests pass.

Add a `workflow_dispatch` trigger with a boolean-ish `all` input, and make each `changes` output evaluate to true when the event is `workflow_dispatch` and `all` is true. This is the mechanism by which criterion 1 becomes demonstrable on demand: `php-test`, `docs`, and `workflow-check` live in path-filtered jobs that a Go-only change skips, so without a force-all switch there is no way to show every `make verify` target executing in one run. Plan 01-02 uses it for the phase exit gate.

Remove the `go` job. Update `result.needs` to list `cache-prime`, `lint`, and `go-verify` in place of `go`; do not rename the `CI passed` job. Reuse every action SHA already present in the file verbatim — no new or floating action references.

In `.golangci.yml`, delete the `run.concurrency` key and the `run.timeout` key together with the comment justifying the timeout. In golangci-lint v2 the timeout default is disabled, so removing the key removes a constraint rather than adding one; the falsifiable replacement is the job-level `timeout-minutes: 15` above. Leave `run.tests: true` and every linter setting untouched — QUALITY-06 is about how lint is scheduled, not which linters run.

Do not raise a timeout, do not reintroduce a `go build` warm-up without `-p=1`, and do not treat the repository going public as part of the fix. All three have been tried or ruled out; the reasoning is in the research dead-ends table.

<task type="auto">
  <name>Task 3: Prove partitioning did not weaken the lint gate</name>
  <files>docs/lint-policy.md</files>
  <precondition>Task 2's partitioned matrix is committed, so the six package patterns exist to be replayed locally.</precondition>
  <action>
Resolve the one MEDIUM-confidence assumption in the research (A1): that golangci-lint's `unused` analyser cannot produce cross-partition false positives, because an unexported identifier is reachable only from its own package and `run.tests: true` keeps test-only helpers counted as used. The reasoning is sound but unconfirmed against golangci-lint's actual behaviour, and if it is wrong the partitioned matrix either emits false positives that get suppressed with nolint directives — a real quality loss — or silently misses dead code.

The mitigation is a direct comparison. Run the linter once over the whole module, then once per partition using the exact `packages` strings from `ci.yml`, and diff the two sorted issue sets. They must be identical.

This is the one task in the phase that compiles the full multi-provider graph on the local machine. Per AGENTS.md, parallel Go builds on this 16 GB Mac have caused kernel panics: every invocation must be serial (`GOMAXPROCS=1 GOFLAGS=-p=1`), run one at a time in a plain Terminal rather than concurrently, and the aggregate partition must not run alongside the whole-module run. If swap climbs or the machine crawls, abort, reap orphaned toolchain processes, and retry later — do not work around it by parallelising.

Record the outcome in `docs/lint-policy.md`: the comparison method, whether the issue sets matched, the six partitions and why the import graph forces them, and an explicit note that these measurements were taken while the repository was private on a 2 vCPU / 7 GB runner, so the numbers must not be re-read as post-publication figures. Also record the documented fallbacks in preference order, so a future OOM has a decided answer rather than a fresh debate: give a partition its own reduced linter set only as a last resort, and split `./internal/cloud/kube/...` out of `core` into a seventh partition if `core` turns out to be the one that struggles.

If the issue sets differ, do not proceed and do not suppress the difference. Report the exact delta — that finding invalidates the partition scheme and needs a decision, not a nolint directive.
